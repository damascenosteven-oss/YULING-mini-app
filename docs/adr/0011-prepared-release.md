# 准备完整包与服务器发布分离

## Critic Loop

问题：手机 publish 把源码下载、运行环境、依赖、构建、审计、视觉验证和 SSH 切换串成一项操作。当前 #10 在审计网络故障时失败，SSH 尚未调用；给 SSH 增加超时不能解决该步骤。

第一版云端直传只加时 40/100：保留已验证云端构建，但约 10.4 小时的实测速率推算超出单个 hosted job 六小时限制。现有路径只补审计重试 65/100：成本小，但发布仍依赖联网构建。准备完整包后单独发布 90/100，接受：新增本机包目录和两步手机操作，换取发布只校验并传输同一个已验证包。

## 决定

prepare 和 publish 是两个请求；准备成功只代表包可发布，不代表服务器已更新。完整不可变包与 source SHA、runtime/engine/lock 摘要和证据绑定。审计 24 小时有效，过期 prepare 只刷新审计，不能将损坏包重新接受。发布只接受当前受保护 main，仍需要 GitHub 控制接口和受限 SSH。

审计在构建器中显式执行而非缓存的 Docker RUN；CI 和电脑使用同一路径，不跳过安全检查。准备不具有服务器操作能力，发布不触发构建。服务器协议保持 schema 1；仅手机/电脑请求升级 schema 2。保留两份本机已接受包，不增加服务、镜像仓库、COS 中转或新权限。

完整发布和普通 PPT 业务验收由所有者手机触发后另行核实；本决策不声称已经部署或 Mac 批准。
