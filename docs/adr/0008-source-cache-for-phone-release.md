# 为手机发布接力缓存已验证的源码提交

## Critic Loop

问题：电脑接力仍在每次手机发布时重新克隆应用和固定引擎。真实运行 #4 和 #5 分别在这两个 GitHub 下载阶段发生 TLS 中断，服务器没有收到包；本机同版本的完整镜像与 12 页重复捕获则通过。GitHub 代理链路偶发失败是当前证据支持的范围，不能由此断言运营商根因。

保持现状 30/100：实现零成本，但继续要求所有者反复手机重发，且可能再次失败。每次完整下载并最多三次重试 68/100：实现简单，但每次发布都依赖不稳定连接，网络请求和等待持续存在。仓库外完整提交缓存并对缺失提交有限重试 88/100，接受：已核对版本可直接复用；代价是约几十 MiB 的本机缓存、完整性验证和异常状态维护。

## 决定

应用与固定引擎分别使用受限的本机 Git 缓存，来源 URL 固定为现有两个仓库。缓存只按完整提交 SHA 命中，验证对象完整性和来源。缺失时获取完整对象，最多三次、每次 90 秒，间隔 2 秒和 5 秒；失败不触发上传或激活。缓存损坏或来源不符时停止并报告，不静默修复或替换为旧版本。

GitHub Deployment 请求、受保护 main 与 Checks 仍由实时 API 核对。源码重试是先前“发布请求不自动重试”的唯一例外；上传和服务器切换保持单次执行。只在所有者审核合并后准备电脑缓存，正式发布仍由所有者手机手动触发。
